# 단계별 빌드 분담과 채울 것

- 일시: 2026-08-01
- 상태: 제안 (0번 확정 전까지)
- 참여: 미정 — 담당 칸은 팀 sync에서 채운다

## 맥락

문서 폴더 구조(`context/` `policy/` `design/` `decision/` `develop/`)는 생겼지만
하네스가 인풋에서 아웃풋까지 이어지지 않는다.

- `.claude/agents/` — stage agent **0개**
- `start/SKILL.md` — 단계 표·실행 순서가 전부 주석 상태
- `docs/PRD.md` — 아직 안내문 (예시 PRD 미복사)

폴더는 "산출물을 어디 둘지"만 정한 상태고, 그 산출물을 만들 주체가 없다.
각자 stage agent를 만들기 전에 **무엇을 채워야 점수가 오르는지**와
**입출력 계약**을 먼저 맞춘다.

## 선택지 — 산출물 경로 계약 (조장이 확정할 것)

`scaffold-harness`는 현재 "모든 중간 산출물은 `docs/artifacts/{NN}-{slug}.md`"라고
못박고 있는데, 이는 `context/`·`policy/`·`design/{slug}/`를 쓰기로 한 구조와 충돌한다.

1. **주제 폴더 + artifacts 병용** — PRD별로 의미가 남으면 주제 폴더,
   이번 실행에만 의미 있으면 `docs/artifacts/`.
   `scaffold-harness` 수정 필요 (공용 파일, 조장 승인).
2. **artifacts 단일** — 하네스는 `docs/artifacts/`만 쓰고, 주제 폴더는 사람이 쓰는 문서로 둔다.
   승인 불필요. 대신 `context/`·`policy/`는 자동 생성이 아니게 된다.

**이 결정이 먼저다.** 확정 없이 각자 agent를 쓰면 입출력 계약이 어긋난 여섯 개가 나온다.

## 전체 플로우

```
docs/PRD.md + 작업 Page 이름(인자)
   ↓ ①해석           → 화면 목록 + context/
   ↓ ②정책 ∥ ③시스템  → policy/{slug}/ + design/{slug}/
   ↓ ④저작           → Penpot {내 Page}에 화면
   ↓ ⑤검증           → 99-verify.md
   ↓ ⑥이관           → 중간공유 → 최종제출
```

②와 ③은 서로 읽지 않으므로 병렬. ④는 둘 다 필요.

## 단계별로 채울 것

점수 4항목(레이아웃·정렬 / 타이포·컬러 / 완성도·디테일 / PRD 충족도) 중
각 단계가 책임지는 축을 기준으로 정리한다.

### ① 해석 — PRD 충족도

이 단계가 게으르면 뒤에서 아무리 잘 그려도 화면이 모자란다.

- **환원 규칙표** — 유저 스토리 동사 → 화면 종류 매핑을 고정한다.
  "확인하고 싶다"→결과 화면, "진입점"→목적지 화면, "정렬/필터"→바텀시트,
  "유료 열람"→결제 모달+성공+실패. 규칙이 없으면 실행마다 화면 수가 들쭉날쭉하다.
- **상태 축 전개** — 화면마다 기본/빈/로딩/실패 중 PRD 4절이 언급한 것을 별도 화면으로 펼친다.
- **추적성** — 화면마다 근거가 된 PRD 문장을 인용해 붙인다. ⑤가 이 표를 채점표로 쓴다.
- **플로우 폐쇄 검사** — 진입 경로가 없거나 나가는 곳이 없는 화면이 남으면 실패 처리.

산출: 화면ID / 이름 / 근거 PRD 문장 / 진입 / 상태 / 필수 요소

### ② 정책 — 완성도·디테일

"실제 서비스라 믿을 만한가"는 대부분 콘텐츠에서 갈린다.
Lorem ipsum이나 "제목 1"이 하나라도 보이면 그 항목은 무너진다.

- **진짜 같은 더미 데이터 세트** — 리스트 화면당 8~12행을 실제 도메인 어휘로 미리 쓴다.
  길이가 제각각이어야 진짜로 보인다.
- **숫자·단위 포맷 규칙** — 천단위 콤마, 등락 부호와 색, "3분 전" 같은 상대 시간.
- **화면 골격 상수** — 앱바 높이, 좌우 패딩, 하단 CTA 높이, 카드 간격.
  ④가 이 값만 보고 그리게 만든다 → 레이아웃·정렬 점수.
- **빈/로딩/실패 문구** — ③의 voice 가이드를 적용해 미리 확정한다.

### ③ 디자인 시스템 — 타이포·컬러

- **웹에서 구한 design.md와 `기존파일` Page가 충돌하면 기존파일이 이긴다.**
  과제가 기존 자산의 리디자인이라, 외부 문서 값으로 덮으면 기존과 무관한 화면이 된다.
  외부 문서는 **비어 있는 칸을 채우는 용도**로 한정한다.
- **타이포 스케일은 5~6단까지.** 단이 많으면 위계가 오히려 흐려진다.
  색은 primary 1 + neutral 6~8단 + semantic 3 정도. 도메인 필수색(상승/하락 등)을 빠뜨리지 않는다.
- **출력을 문서로만 내면 ④가 못 쓴다.** `develop/scripts/tokens.js` 같은
  JS 상수 파일로도 같이 낸다. 저작 전 `penpot.fonts.all`로 폰트 존재를 확인한다
  (없으면 에러 없이 조용히 대체된다).

### ④ 저작 — 레이아웃·정렬 + 함정 방어

- **컴포넌트를 먼저 만들고 인스턴스로 화면을 조립한다.** 이름·구조는 처음에 확정.
  나중에 이름을 바꾸거나 자식을 지우면 플러그인이 멈춘다.
- **캔버스 배치 규칙** — 화면을 격자로 일정 간격 배열하고 이름을 화면ID로 단다.
  파일을 열었을 때의 첫인상이라 체감 점수가 크다.
- **실사진을 쓴다** — `uploadMediaUrl`. 회색 박스와 완성도 격차가 크다.
- **상태 변형은 `clone()`** — 모달·에러·로딩을 처음부터 다시 짓지 않는다.
- 함정 대응이 전부 이 단계다: fills는 penpot 형식, 스크립트 첫 줄에서 Page 재고정,
  오버레이는 뒤 보드 `opacity`로, 마지막에 auto-height 텍스트 전부 `resize` 재계산.

### ⑤ 검증 — 점수 확정

- ①의 필수 요소 체크리스트를 그대로 돌며 O/X
- **텍스트 클리핑 스캔** — 잘린 글자는 완성도 점수를 즉사시킨다
- **정렬 편차 스캔** — 같은 역할 요소들의 x좌표·여백 어긋남 검출
- export PNG가 비면 **재-export 한 번** 후 판단
- 실패 시 어느 단계로 되돌릴지 명시

### ⑥ 이관 — 현재 아무 데도 없음

`중간공유`·`최종제출`로 옮기는 절차가 정의된 곳이 없다.
심사 대상이 `최종제출` Page라 이게 빠지면 결과물이 심사에 안 올라간다.
